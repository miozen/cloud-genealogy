# P0-5 房支结构变更：设计审查

状态：已确认；阶段 A、阶段 B 的最小发布链路已完成并在 local D1/Worker 验证。最后更新：2026-10-24。

## 已验证现状

- `branch` 是以稳定 ID 表示的当前结构表，包含 `lineage_id`、可空的 `parent_branch_id`、名称、类型及 `retired_at`；当前没有写入 API、版本号、同世系父房校验或无环约束。
- `branch_membership_snapshot` 已按 `lineage_revision` 完整快照，但它只保存 `branch_id`，不保存房支的名称、父房或类型。现有 published revision 因而不能自行重建历史房支结构。
- `account_scope` 可引用房支。权限只认提案基准 revision 中精确房支的 `blood_primary` 成员；不递归子房，也不从承谱关系推导。
- 当前成员增删提案会在完整 revision snapshot 中原子发布，且回退能生成成员差异；它不适合承载房支创建、改名、父房移动、合并或退休。

## 已确认的约束

- `agnatic`、`migration`、`administrative` 是不同业务类型，不能从亲属关系推导，也不应在现有房支上改写类型。
- 已发布 revision、原始来源和审计日志不可物理删除；高风险变更需要预览、双人职责分离、审计和可恢复路径。
- 房支成员增删首切片只处理既有、未退休房支，且仅管理员可以操作。

## 风险结论

直接更新当前 `branch.name` 或 `branch.parent_branch_id` 会改变所有历史 revision 通过同一 `branch_id` 读取到的结构含义；直接删除房支还会破坏成员快照和账号范围。因此在引入**按 revision 保存的房支结构快照**之前，不应开放任何房支结构写 API。

## 推荐的两阶段方案

### 阶段 A：先建立可回放的结构快照（前置）

1. 引入 `branch_structure_snapshot`，每个 published revision 保存 `branch_id`、`parent_branch_id`、名称、类型、状态和排序键的完整快照；历史读取只使用该快照，不回读可变 `branch`。
2. 引入独立 `branch_structure_change_item`，至少区分 `create`、`rename`、`retire`；不得复用成员或关系条目。
3. 创建新 revision 时，先复制基准结构快照，再应用结构条目和成员条目；同一 D1 batch 写 revision、结构/成员/关系快照、pointer、提案状态与审计。
4. 回退提案必须比较并生成明确结构差异；不直接将 published pointer 指向旧 revision。
5. 为现有历史 revision 回填当前结构快照仅在“此前尚无结构写 API”的前提下可接受；迁移应先在本地 D1 验证并记录该假设，preview/production 仍须单独授权。

### 阶段 B：最小可用结构操作（已完成）

仅管理员可创建、提交、审核和发布；审核人与创建人不同。首批仅支持：

- 在同一世系创建新房支；父房可为空或为同世系现存活跃房支。
- 对现存活跃房支改名。
- 退休无子房、无当前成员、无活动 `account_scope` 引用的房支。

移动父房、跨世系迁移、合并、拆分、改变 `branch_kind` 和物理删除均延后。它们需要额外的成员重归属策略、范围授权迁移、冲突呈现与恢复设计，不能作为“编辑名称”的副作用。

## 必须校验和审计

- 父房与子房属于同一 `lineage`，结构无环；名称在同一父房下的唯一性规则需在实现前确认。
- `branch_kind` 创建后不可变；退休房支不可新增成员或成为新父房。
- 退休前必须先通过成员变更提案迁走当前成员，并显式移除/替换账号范围；系统不得静默扩大或迁移编辑权限。
- 基准 revision/pointer 变化进入 `conflicted`，不自动重放结构变更。
- 预览须显示结构树差异、受影响成员、受影响账号范围和任何被阻止原因；理由、操作者、审核人和发布版本写入审计。
- 任一 batch 失败时不得部分创建房支、写结构快照、切换 pointer、发布成员变化或落审计。

## 本轮实现边界与验证

- 结构提案与成员、关系提案使用同一审核与发布链路。发布 batch 先写当前 `branch` 的 create/rename/retire，再写新 revision 的结构快照、成员/关系快照、published pointer、提案终态和审计；任何一句失败则整批回滚。
- 批准与发布都会从基准结构快照重建结构候选；重复同级活跃名称、退休房的改名、无效父房及含活跃子房的退休均会被拒绝。
- 退休还会拒绝候选成员快照仍含该房支，或任一 `account_scope` 仍引用该房支的提案；权限不会自动迁移或扩大。
- 已实际通过 `npm run check`（22 个 Vitest 文件、50 项测试）及 `npm run test:local-auth`。后者以第二名管理员审核并发布房支改名，并断言当前 `branch` 已更新；未执行 remote/preview/production 写入或部署。

## 需确认的业务决定

1. 是否接受“先建立 revision 级房支结构快照，再开放任何结构写入”的前置条件？**建议：是。**
2. 阶段 B 是否仅支持创建、改名和受限退休，并将移动、合并、拆分、类型修改另开切片？**建议：是。**
3. 同一父房下是否要求活跃房支名称唯一（建议：要求；根房也视为同一空父房）？**建议：是。**
4. 退休是否必须无子房、无当前成员、无活动账号范围引用（建议：必须；先以显式提案处理依赖）？**建议：是。**

## 验收

- 任一历史 revision 的房支树、成员归属与显示名称均可独立重放，后续改名/移动不改变历史解释。
- 跨世系父子、循环、重复同级名称、退休房支新增成员、自审和陈旧基准均被拒绝。
- 结构/成员混合提案的预览与发布要么全部生效，要么不留下任何结构、snapshot、pointer、提案或审计的部分写入。
- 本地 D1/Worker 回归覆盖创建、改名、退休拦截、回退差异及发布失败原子性；不执行 preview/production 迁移或部署。
