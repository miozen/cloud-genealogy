# P0-6 local-only 幂等账本关联完整性评审

状态：2026-10-31，仅本机隔离夹具；不连接 Cloudflare、不读取真实凭据、不接入人工审批或远程执行。检查通过只表示满足测试约束，不证明操作历史或来源真实。

## 测试约束

`fixture_challenge_request` 对 `(kind, challenge)` 增加唯一索引，防止同一测试挑战被两个相同类型请求登记。新建测试数据库包含该索引；这不是业务 D1 迁移。

`scripts/local-orphan-ledger-integrity-fixture.mjs` 在锚点匹配后、幂等执行和查询时检查测试账本：外键引用、请求及挑战 ID/摘要形状、签发与消费审计数量、挑战消费状态、每个挑战同一操作最多一条请求、请求成功标记，以及签发请求输入摘要与关联挑战 scope 的一致性。消费历史在被查询或重试时还重新核对请求中签名所绑定的挑战和该挑战 scope。新增请求写入后也重新执行检查；检查或审计失败时回滚。

为兼容既有测试夹具，直接使用旧 `issue` / `consume` 的挑战可以没有幂等请求记录；它们仍必须有与状态一致的审计。因此完整性通过**不表示所有账本操作都经过请求 ID 或受控入口**。检查当前全表扫描，只用于少量隔离数据，不是生产规模方案。

现有 `observeFixtureState` 仅比较摘要，不运行上述关联检查；若损坏数据已被当作基线，它仍可能报告 `ready` 和 `matches_current`，但输出始终为 `review_required`。只有幂等查询和执行会进行本轮关联校验，不能把摘要匹配视为数据完整性结论。

正常历史签发记录在挑战后来被消费后仍可查询，其 `accepted` 为 null、结果标记 `review_required`，不宣称挑战当前可用。查询必须重新满足现有锚点条件；监督器消失、重启未初始化、pending 或摘要不匹配均拒绝，检查不会重新 bootstrap 或解锁。

## 故障覆盖与明确反例

测试在建立监督器基线前注入签发摘要错误、缺少签发/消费审计、未提交消费却有成功记录、无效结果、相同挑战的重复请求，以及关闭外键后写入的孤儿引用；即使人为把损坏账本设为基线，幂等查询和执行仍拒绝。另测试唯一索引、把消费请求链接到不同挑战但保留原输入摘要、签发结果后来消费、监督器丢失及重新启动。原有测试继续覆盖真实本地并发、提交边界中断和库回退。

反例同样重要：两个签发请求使用相同 scope，数据库所有者去除约束并交换它们关联的挑战，再用篡改后的数据库重新 bootstrap 监督器，结构检查仍可通过，查询会返回被交换的挑战。由于只保存输入摘要而没有独立可信的请求—挑战绑定证据，无法仅凭本数据库判断真实签发历史；未查询的消费请求也无法从摘要重建其原始签名输入。监督器和数据库被同一主体控制或一起回滚时，现有索引、触发器和检查均不构成防篡改证明。

本轮不修复损坏、不删除数据、不自动解锁 pending 或重设锚点，也不提供真实审批。监督器失陷、旧入口/直接 SQLite 写入、密钥被盗、可信时间缺失、SQLite COMMIT 内部或掉电故障仍未解决；不得启用远程执行。

`npm run test:local-orphan-anchor` 包含关联漂移及反例；challenge、signature、recovery、windowed mock 回归需分别执行。
