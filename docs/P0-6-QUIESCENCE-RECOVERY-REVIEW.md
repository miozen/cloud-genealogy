# P0-6 直传与中断写入的静默恢复审查

状态：风险已定位，本地故障注入与只读诊断；恢复执行未实现，remote 备份仍禁用。2026-10-28。

## 现有事实

- 预签名 PUT URL 在过期前可重复使用；即使上传完成或客户端失联，服务端不能据此证明该 URL 未再次使用。R2 文档不在此提供已开始 PUT 的排空证明。[R2 预签名 URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)
- HTTP Worker 在客户端保持连接时没有固定执行时长上限；发生进程崩溃或中断时，`finally` 不保证运行。[Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- 活动准入记录只能证明请求被准入，不能证明其仍在执行或已经停止；D1 本身不能根据记录年龄判断一个 Worker 是否还会继续写入。
- 意图时间与 URL 签发时间现共用同一时钟；历史记录并不因此获得追溯修复。`uploadsDrained` 与 `remoteExecutionAvailable` 均固定为 false。

## 可选方案及限制

1. **保持直传并依赖外部运维隔离**：操作人员停止所有写入口并取得 R2/Worker 侧可靠排空证据；实现简单，但目前没有可验证的通用排空接口或证据契约，不能自动宣布成功。
2. **改为服务端受控上传及可取消执行**：可以将请求纳入准入记录，但进程死亡、R2 子请求状态不明和 D1/R2 非原子性仍需明确恢复协议；仅将 PUT 代理给 Worker 不会自动解决问题，也会改变既有直传设计与性能边界。
3. **对所有写操作实施持久化 fencing**：每个 D1 业务写入必须与有效代次原子绑定，R2 写入需要额外隔离策略；可形成更强保证，但涉及大量已有写路径与迁移，需要完整并发设计和测试。

推荐先对方案 3 做原型和完整写路径盘点，同时保持当前直传及远程备份禁用；不得通过删除/完成准入记录、固定等待或单人填写布尔值绕过阻断。

## 独立原型（2026-10-28）

`scripts/fencing-prototype.mjs` 使用 Node 的内存 SQLite 与内存 Map，不接入应用或 Cloudflare。冻结原子递增代次；写入在 SQLite 事务中校验代次并提交业务行及审计。模拟的暂存 key 按代次隔离，发布时复制成独立副本。`npm run test:fencing-prototype` 覆盖冻结前后旧请求、冻结释放后旧请求恢复、事务中断回滚、旧暂存对象晚到覆盖和对象复制后 D1 发布失败。

最后一项故障显示对象副本可能成为无数据库记录的孤儿，后续同键重试也被阻止。原型没有自动清理或恢复该状态：真实设计必须增加可审计的逐项恢复状态，并证明真实 R2 发布对象不能再被旧凭据覆盖。内存对象复制不代表 R2 的不可变性，也不证明 D1/R2 跨服务原子性；Node SQLite 测试不替代 Wrangler local 或远程平台验证。现有业务写路径尚未接入 fencing，不能启用真实备份。

## 本地诊断与故障注入

管理员只读 `GET /api/admin/backup-write-freeze/blockers` 最多列出 100 个开放准入和 100 个未完成/未过期上传，并报告截断；不清除记录，也不提供恢复写入接口。完成记录写入失败时故障注入保留未完成状态；处理函数抛错且 finally 正常执行时才完成记录。真实 Worker 崩溃、R2 中断 PUT 和线上平台行为尚未实测，不能称为已恢复或收敛。
