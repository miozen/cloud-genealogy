# P2 媒体到期清理：安全协议设计审查

状态：第 39 项设计审查完成；**未获明确确认前不得实现清理执行、Cron、R2 删除或 D1 删除。**最后更新：2026-10-25。

## 1. 结论与边界

现有 `GET /api/admin/media-assets/cleanup-preview` 只产生管理员可读的候选列表；它不读取 R2、不写 D1、不写审计、不删除对象。该端点不是删除授权，也不能作为稍后执行删除的稳定快照。

当前不能开启真实清理，原因有二：

1. P0-6 尚未具备经演练验证的 remote 备份与恢复点，删除后不能证明可从异地备份恢复对象；
2. `person_media` 保留历史关联并以外键指向 `media_asset`。物理删除 D1 资产行会破坏历史可追溯性或被外键阻止。

推荐方案是：**删除 R2 字节后保留 D1 墓碑，不物理删除媒体元数据或历史关联。**这比“删对象再删记录”更符合现有审计、外键和恢复边界。

## 2. 已确认事实

- 仅 `retired` 资产有 `retired_at` 与 `cleanup_after`；活动关联清零后才会进入该状态。
- `media_asset_state_cleanup` 索引已经覆盖状态、截止时间和 ID；预览只选择已过截止且没有活动 `person_media` 关联的资产。
- 媒体读取端点只允许 `active` 资产，因此退休资产在清理前已不可由正常读取路径访问。
- local 备份恢复演练已覆盖保留期内的退休媒体，但 remote 备份、远程媒体恢复和生产切换均未完成。
- 当前 Cloudflare R2 Worker API 的对象删除在成功返回后具有强一致可见性；单次 API 调用最多删除 1000 个键。项目不应依赖这一上限实现无界或自动化清理。参考：[R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)、[R2 一致性模型](https://developers.cloudflare.com/r2/reference/consistency/)。

## 3. 推荐的数据与状态扩展（待确认）

在实际编码前，建议通过前向迁移补充如下概念，而不是复用预览结果直接调用 `MEDIA.delete()`：

| 概念 | 最小字段/规则 | 目的 |
|---|---|---|
| `media_cleanup_run` | ID、候选快照哈希、创建者、创建时间、失效时间、状态、第二确认者/时间、备份恢复点标识 | 固定一次人工审阅的候选集合，防止预览与执行之间漂移。 |
| `media_cleanup_item` | run ID、media asset ID、预期 key/SHA-256/大小、预期 `retired_at`/`cleanup_after`、逐项状态、错误摘要、R2 删除时间 | 逐项重试和审计，不重新扫描扩大批次。 |
| `media_asset` 墓碑状态 | 新增 `purge_pending`、`purged` 及 `purged_at`、cleanup run ID；原有哈希、key、大小、MIME、退役时间保留 | 维持外键与历史关联，明确对象字节已被删除。 |

`purged` 资产必须继续不可读取、不可重新关联、不可重新上传到同一 key。若未来要恢复，必须从已验证备份生成**新的**资产 ID 与对象 key，并写独立审计，不能把墓碑重新激活。

## 4. 推荐执行协议（待确认）

1. 管理员获取只读预览；系统在创建 run 时重新查询并在同一 D1 批处理内冻结固定的资产 ID、预期元数据和候选快照哈希。run 默认 24 小时失效，过期后只能重新预览并冻结。
2. 创建 run 前，操作者必须填写并由系统记录一个经验证的异地备份恢复点标识、包哈希和演练结果。当前缺少该能力，因此实际 run 创建端点不得上线。
3. 第二位管理员在有效期内审核固定候选、备份标识和影响数量后确认。第二确认人不得等于创建人；任何候选变更、过期或撤销都使确认失效。
4. 执行端逐项重新核验：资产仍为 `retired`、`cleanup_after` 已过、没有活动关联，且对象 key、SHA-256、大小、退役/截止时间均与冻结项一致。不符则标记为 `skipped_changed`，绝不删除。
5. 通过重新核验后，先在 D1 标记该资产为 `purge_pending` 并写审计；再删除其唯一 R2 key；成功后用 D1 批处理写为 `purged`、记录时间和逐项审计。每次请求只处理小而固定的页（建议不超过 100 项），可暂停、可恢复。
6. R2 删除失败时保留 `purge_pending` 和错误摘要，不修改为 `purged`。重试只针对同一冻结项，并再次执行第 4 步；不自动扩大候选范围。
7. 若 R2 删除成功而最终 D1 写入失败，run 状态为 `r2_deleted_pending_finalize`。恢复程序只重试 D1 收尾和审计，不假定对象仍存在，也不尝试以相同 key 重建对象。
8. 完成后保留 run、item、`media_asset` 墓碑、历史 `person_media` 和全部审计。只有在确认的备份保留期之外，才可另行评审历史运维记录归档；不在本协议范围内。

## 5. 禁止事项

- 不使用 R2 lifecycle rule、Cron、Dashboard 多选删除或全桶扫描替代上述受控流程。
- 不接受客户端提交对象 key、资产 ID 列表或预览时间作为执行真相。
- 不把“R2 已删除”当作“D1 已安全收尾”，也不把“D1 标记成功”当作“R2 一定不存在”。
- 不在 preview 或 production 上用真实对象试错；首次实现只允许隔离 local D1/R2 夹具。
- 不物理删除 `media_asset`、`person_media` 或 `audit_log`，也不覆盖历史对象 key。

## 6. 首次实现前的批准项

以下事项尚未确认，必须由项目负责人明确批准后再编码：

1. 采用 D1 墓碑而非物理删行；新增 `purge_pending` / `purged` 状态和清理 run/item 表。
2. 是否强制两位不同管理员确认，以及 run 的有效期（建议 24 小时）。
3. 可接受的已验证异地备份恢复点定义、最长有效期和记录责任人；在 P0-6 remote 恢复演练完成前是否完全禁用执行。
4. 单次执行页大小（建议最多 100）、失败重试次数和人工升级路径。
5. 首次 local 演练完成后，是否授权单独的 preview 合成对象演练；production 清理必须再次单独授权。

## 7. 未来验证清单

- 未授权、单人、过期确认或篡改候选均不能创建或执行 run。
- 新活动关联、修改截止时间或元数据变化会令冻结项跳过，且不调用 R2 删除。
- R2 删除失败、删除成功后 D1 收尾失败、重复请求和中断重试均有确定状态与审计。
- `purged` 墓碑、历史人物关联与审计能在备份恢复后保留；正常读取和重新关联始终拒绝该资产。
- 完整 local 演练通过后，再由独立授权决定是否进行 preview 合成对象演练；不以 local 成功替代 remote/production 证明。
