# P0-6 本地备份冻结窗口模型

状态：仅供本机测试的 SQLite 原型，2026-10-31。它不接入 Worker、实际备份脚本、D1/R2、凭据或远程资源，也不是生产租约、恢复授权或一致性证明。真实远程执行保持禁用。

## 目的与建模范围

针对“导出前后各读一次冻结状态，期间可能解除、写入、再冻结”的缺口，验证一个有代次的窗口如何在跨步骤过程中保守失效。模型中的冻结、时间、持有人、证据、五个步骤和数据库均为本地模拟；证据仅是夹具记录，绝非可信排空证明。模拟步骤是 `d1_export → media_inventory → media_download → verify → finalize`，不实际执行这些操作。

## 状态与规则

1. 模拟冻结 ID 唯一，每次新冻结递增代次；解除时在同一 SQLite 事务使仍被持有的窗口失效。再次冻结不能恢复旧窗口，旧证据不能用于新代次。
2. 合成证据绑定冻结 ID、代次、修订号和过期时刻；窗口绑定单个持有人与证据版本。一个夹具数据库同一时刻最多一个 `held` 窗口。缺失证据、错误范围、到期或撤销不可获得窗口。
3. 每个步骤开始和结束都重新校验窗口、持有人、冻结 ID/代次、证据修订/撤销及时间；失效时持久化 `invalidated` 与原因，不能用新证据复活。步骤必须顺序执行，进行中的步骤不能再次开始；最近一个已结束步骤的重复结束幂等，不重复记审计。
4. 模拟时钟不允许倒退；窗口操作发现倒退会保守失效。证据仅在边界检查时发现过期，不假装存在后台定时失效。实际系统必须另外解决可信时钟、证据来源、撤销传播和跨服务时序。
5. 一旦模拟进程重启，所有仍为 `held` 的窗口都标记为 `invalidated/process_interrupted`，不自动续租或重试可能产生外部副作用的步骤。只能通过新的有效冻结和新窗口重新开展；模型没有自动处理临时输出或外部对象。
6. 仅当五个模拟步骤顺序结束且最后一次校验通过，模型才记录 `completed`。它仅是一次模型操作完成的历史事实；结果中的 `remoteExecutionAvailable` 恒为 false，不是实际备份完成或任何部署/执行授权。

## 本地故障与并发测试

`npm run test:local-backup-window` 使用 Node 22 的 `node:sqlite` 和隔离内存/临时磁盘 SQLite；2026-10-31 首轮 21 项测试通过，mock 组合增量加入同步发布回调约束后共 22 项测试通过。覆盖正常顺序、解除/重冻、冻结 ID 不复用、证据到期/撤销/版本变化、时钟回退、错误持有人、并发持有、步骤顺序、幂等记账及进程重启阻断。

子进程在模拟步骤开始事务的 COMMIT 前以及 COMMIT 返回后分别 SIGKILL：前者验证标记和审计回滚，后者验证标记保留；两者重启后都使窗口失效。另以两个独立 SQLite 进程竞争窗口，确认只有一个持有及一条获得审计。测试不是在 COMMIT 系统调用内部杀进程，也不证明掉电持久性。

## 尚未解决

- 模型的状态与正式 Worker 的冻结、readiness、外部写者隔离或真实证据没有绑定；调用方可自行构造证据和时间，不能作为安全边界。仅有隔离 mock 组合使用可注入测试钩子，详见 `P0-6-LOCAL-WINDOWED-MOCK-BACKUP.md`。
- 单个 SQLite 事务无法让 D1 快照与 R2 操作原子化；既有直传 URL 及在途 PUT 的排空、真实对象不可变性和跨实例证明仍未解决。
- 外部操作可能在步骤标记与中断之间产生副作用；真实实现需要逐项清单、对象隔离、失败清理和可审计恢复。独立模型没有数据包；mock 组合仅使用本地夹具，也不能证明真实导出完成或远程清理成功。
- 如需未来接入，须先评审可信证据、冻结窗口的持有/撤销与 fencing、时钟、重启所有权、恢复和持续验证协议；任何远程操作仍需单独授权。
