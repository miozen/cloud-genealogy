# P0-4 历史谱书阅读布局：设计审查

状态：设计审查完成，实施待项目负责人确认。最后更新：2026-10-25。

## 1. 范围与已验证事实

本切片只改善指定 `genealogy_edition` 的**来源关系阅读**。它不改变来源记录、关系词解释、统一世系、差异判断或发布 revision。

- 历史投影只接受指定版本的 `source_person_record`、未撤销 `source_relation_claim` 与活动语义规则；节点主键是 `sourceRecordId`，即使未映射到 `person` 也保留。见 `worker/lineage/historical-lineage-projection.ts`、`worker/app.ts`。
- 只有显式解释为父子关系的来源主张才产生有向边；未知词、非图关系、缺端点分别保留为 `pending_interpretation`、`not_graphable`、`incomplete`，而不是猜测。配偶主张已在投影中保留为 `spouseEdges`。见同一投影模块。
- 当前 `layoutHistoricalRecords` 只是按来源记录输入顺序排成稳定方格；它刻意不推导世代。前端目前只绘制 `parentChildEdges`，没有绘制 `spouseEdges`。见 `src/historical-record-layout.ts`、`src/App.vue`。
- `source_relation_claim` 可表达冲突、多父母、环和未映射记录；它不受统一承谱的“单一上行、无环”约束。见 `migrations/0004_core_genealogy_model.sql`、`docs/DATA_MODEL.md`。
- 历史投影和比较接口目前均限 `system.manage` 管理员；没有完成面向会员/访客的来源原文、节点或字段可见性策略。见 `worker/app.ts`、`worker/auth/authorization.ts`。

因此，不能将历史来源图改造成“看起来像统一世系”的树，也不能用统一 revision 的边补齐来源断点。

## 2. 已确认约束

1. 节点必须持续使用来源记录 ID；`confirmedPersonId` 只能作为可选对照信息，不能替换节点、合并同名或填补缺失边。
2. 每条线应能回溯到 `claimId`、原始 `relationKind`、`rawText` 和解释后的父母类型；布局不得丢弃冲突证据。
3. 未解释、非图、缺端点、未映射和冲突是阅读结果的一部分，不能被静默过滤或标成统一差异。
4. 布局为纯 TypeScript，输入是历史投影，输出 SVG 坐标与连接点；不得读 D1、调用 Vue DOM 或引用 canonical snapshot。
5. 首版继续只对管理员开放；扩展读取角色前须另行落实服务端节点、边、原文和字段级隐私过滤。

## 3. 推荐的最小实现（待确认）

### 3.1 受限 API 与读模型

保留历史投影的来源独立性，并为阅读图增加独立、显式受限的 endpoint（或在已有历史投影 endpoint 上采用同等契约）：

```text
GET /api/admin/genealogy-editions/{editionId}/historical-projection?rootRecordId={optional}&maxNodes=100

{
  view: "historical",
  editionId,
  projection: { nodes, parentChildEdges, spouseEdges, annotations },
  truncated: boolean
}
```

- 默认最多 **100 节点、200 条已解释关系**；服务端按来源记录的稳定 `created_at, id` 顺序和 claim 的 `created_at, id` 顺序截断。
- `rootRecordId` 存在时，只从该来源记录沿显式已解释边做至多两跳的无方向邻接读取，仍遵循相同上限；它不是按统一人物 ID 查询。
- 达到限制时返回 `truncated: true`，不返回被截断节点/关系的 ID、姓名或数量。未解释/不完整主张在被选中节点范围内仍照常返回。
- 比较接口继续使用完整的、已确认映射关系语义；阅读布局的截断结果不得被拿来重新判定 `same`、`historical_only` 或 `canonical_only`。

### 3.2 布局规则

建议采用“来源图分层 + 冲突保留”而非树形布局：

1. 对已解释父子边计算强连通分量（SCC）；分量缩点后按最长父到子路径分层。无环部分可得到稳定的“上代在左、下代在右”列。
2. 同一 SCC 的来源记录放在同一冲突组内，组内关系以虚线/冲突标识连接；不拆边、不伪造世代。
3. 多父母、多条来源主张都绘制为独立连线，并附 `claimId` 可追溯标识；同一端点的不同来源不能因视觉去重而消失。
4. `spouseEdges` 以邻接横线绘制，不参与父子分层，也不推导子女或世代。
5. 没有已解释父子边的来源记录放到“未连通来源记录”区，但仍显示原文与注记；它们不能因无边而从版本视图中消失。
6. 节点和组内排序固定为来源记录 `created_at, id`；相同输入必须获得同一坐标，避免无关主张编辑导致布局漂移。

### 3.3 前端交互

- 保留当前统一/历史差异摘要；历史阅读图与比较状态并列呈现，不能以颜色暗示未映射记录是“错误”。
- 节点侧栏显示来源姓名、来源记录 ID、是否已确认映射（仅标识，不自动跳转为统一人物）、直接 claim 原文与解释状态。
- 图例必须区分：生父母、养父母、嗣父母、配偶、冲突组、待解释、非图与不完整；不能只使用一条无标签直线。
- `truncated` 时只提示重新选择图内来源记录作为根；不提供连续自动加载或跨来源 ID 的推断。

## 4. 验收与测试数据

实施后至少覆盖：

1. 三代无冲突来源边按列稳定分层；源记录顺序变化以外的无关主张不改变已有节点排序。
2. 同一孩子存在生父与嗣父、同一端点有两条不同来源主张、配偶边以及一个未映射记录；所有 claim 仍可追溯且不使用 canonical 边补齐。
3. 两节点环和三节点环进入明确冲突组，布局终止且不把环强行展开为树。
4. 未解释、非图、缺端点和未连通记录仍在侧栏/未连通区可见。
5. 101+ 节点或 201+ 解释关系触发服务端截断，返回数据不含边界外标识；`rootRecordId` 只在来源图内邻接。
6. 管理员以外仍为 403；纯布局、Worker/D1 集成、类型检查和构建全部通过，且不使用 `--remote`。

## 5. 需项目负责人确认

推荐先确认以下方案：**管理员专用、默认 100 节点/200 已解释关系、可选来源记录根且最多两跳、SCC 冲突组布局、配偶独立连线、未连通记录不丢弃。**

需要确认：

1. 是否接受 100 节点/200 关系和来源根两跳的边界？
2. 是否接受环以“冲突组”呈现，而不是尝试推断或自动裁断某条原始主张？
3. 当前版本选择为不开放会员/访客读取来源原文；是否保持管理员专用（推荐）？
