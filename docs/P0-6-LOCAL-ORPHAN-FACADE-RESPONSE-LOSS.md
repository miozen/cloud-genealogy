# P0-6 local-only 挑战账本门面与响应丢失评审

状态：2026-10-31，仅本机测试夹具。无人工审批、业务恢复入口或远程执行；不连接 Cloudflare、不读取真实凭据。测试结论不构成可上线的安全承诺。

## 门面与旧入口

`scripts/local-orphan-guarded-facade.mjs` 用冻结的无原型对象只向测试调用方暴露受控 `issue`、`consume`、`inspect` 和 `observe`，不暴露 SQLite 连接及旧方法。测试工作子进程使用这个门面，未知操作名（包括旧接口名）被拒绝，测试可验证其可见方法和账本未变化。

这是**代码级调用约定，不是安全隔离**：工作进程、监督器、测试父进程以及数据库同属受控本机用户，调用方仍可导入旧 `ChallengeFixture.issue` / `consume`、直接访问或替换 SQLite，亦可伪造 IPC、重新 bootstrap 或控制监督器。旧入口仍可在另一个进程或同用户代码中绕过锚点；没有权限隔离、强制访问控制或可信进程身份，不得宣称所有写入已受保护。

## 只读证据与响应丢失

`observeFixtureState` 在本地 SQLite 写锁期间比较账本摘要与监督器状态，返回有限结构：`ready`、`pending` 或 `uninitialized`，以及对应的摘要匹配分类。结果始终是 `review_required` 且远程执行不可用，不输出挑战、签名、密钥或账本摘要。操作最终回滚 SQLite 事务，不修改账本、监督器状态或 pending；通信失败拒绝出具证据。它仅是一次观察，不能证明事务历史、签名者身份、观察真实性或新鲜度，也不解除任何阻塞。

测试通过父进程在监督器已处理 RPC 后丢弃回复，或者在回复前 SIGKILL 工作进程：

- `prepare` 已处理但回复丢失：工作进程等待超时后回滚 SQLite，监督器仍为 pending；重复只读观察显示 `matches_before`，受控消费和签发被阻塞。
- `finalize` 已处理但回复丢失：SQLite 已提交，监督器可能处于 ready 且摘要匹配，但调用方没有成功响应。消费重试被已消费状态拒绝；签发重试可能创建新挑战，原挑战对调用方仍是未知结果。**ready 匹配不会阻止其他新操作，也不证明原调用方收到结果**。当前没有持久请求 ID、幂等结果查询或未知结果全局阻塞。

上述行为在签发与消费各自测试，另外在 prepare/finalize 已处理、回复前实际强杀工作进程。RPC 使用测试用超时，超时不区分明确拒绝与响应丢失，不能推断监督器是否执行；依靠该超时不能证明真实 IPC 或远程系统故障语义。

## 未覆盖与限制

监督器自身死亡会丢失内存锚点，新进程未初始化时拒绝受控操作；不得以当前数据库盲目重新 bootstrap。仅对受控函数和指定交错进行测试，没有不可回滚独立锚点、持久消息收据、双人审批、可信时间或密钥治理。数据库回滚、监督器被控制、签名者造假及两个存储不具备共同事务仍是已知问题。SQLite `COMMIT` 内部中断与掉电未验证。

`npm run test:local-orphan-anchor` 执行本轮门面、响应丢失及进程故障回归；challenge、signature、recovery 和 mock 备份测试继续独立执行。

后续本地请求 ID 及结果查询实验见 `P0-6-LOCAL-ORPHAN-IDEMPOTENCY-FIXTURE.md`；仅在锚点和账本保持时能避免同请求重复签发，并未解决整库回滚、旧入口绕过或真实审批。
