# P0-5 房支成员与对象级审批：设计审查

状态：已确认；首个成员变更切片已实现，待本地完整验证。最后更新：2026-10-24。

## 已验证现状

- `branch_membership_snapshot` 已随 `lineage_revision` 不可变保存，并有“每人每 revision 至多一个 `blood_primary`”约束；`migration` 和 `administrative` 成员可并存。
- 关系提案发布仅复制基准房支快照，不推导或修改成员归属。现有 `change_item` 只能表示承谱边和 canonical 亲属关系，不能承载房支、成员类型及成员变更语义。
- 当前没有房支创建/退休、成员变更、成员来源依据或对象级审批人的写入模型。现有回退提案也只还原承谱和亲属关系，不还原未来可能新增的房支成员差异。

## 推荐的首个成员变更切片

只支持对**既有、未退休房支**的成员归属增删，不支持创建、改名、移动、合并、退休房支，也不修改来源层记录。

1. 增加独立的 `branch_membership_change_item`，而非复用关系 `change_item`；字段应包括 `change_request_id`、`operation(add/remove)`、`branch_id`、`person_id`、`membership_kind`、创建时间与唯一约束。
2. 关系条目与成员条目可属于同一 `change_request`，但预览必须分别展示承谱、亲属关系和房支成员差异。发布在同一 D1 batch 内写入 revision、三类完整快照、pointer、提案终态及审计。
3. 从基准 revision 复制成员快照，再应用成员条目；`blood_primary` 至多一个，但允许零个主房，以保留“房支未知/待接续”人物，不制造虚假归属。
4. 首切片仅管理员可创建、提交、审核和发布成员变更。房支编辑员不得变更成员归属，避免通过变更自身成员资格扩大 `account_scope` 权限。
5. 审核人与创建人必须不同；沿用现有双人职责分离。对象级审批人映射另开切片，在有明确宗族职责、代理和失效规则前不推断。
6. 理由、操作者、预览差异和审计为必填审计链；结构化来源证据关联暂不伪造。后续应在来源/考证模型中建立可多对多引用的证据链接，再将其设为高风险成员变更的必填条件。
7. 回退提案必须同时把目标 revision 的房支成员差异转换为明确成员条目；不能只回退关系快照。

## 必须校验的规则

- 房支存在、未退休，且属于提案的同一 `lineage`；人物存在。
- 增加既有成员或移除不存在成员为结构化校验错误；同一提案内的完全重复成员条目拒绝。
- 应用后的每位人物不得有多条 `blood_primary`；`migration`、`administrative` 不授予房支编辑权限。
- 提案基准变化时进入 `conflicted`，不自动重放成员条目；发布前重新预览和校验。
- 失败 batch 不得部分写入成员快照、pointer、提案终态或审计。

## 已确认的业务决定

1. 首切片只处理既有房支的成员增删，房支结构本身另开高风险切片。
2. 首切片要求变更理由与审计，暂不伪造结构化来源/考证引用；其后单独设计来源链接，再决定何时升级为必填。
3. 继续由任意另一位管理员审核，暂不按房支推断或分配审批人。

## 验收

- 成员草稿不改变已发布快照；发布后新 revision 同时包含关系和成员完整快照。
- 主房冲突、退休房支、跨世系房支、重复条目、陈旧基准和自审均被拒绝。
- 回退生成明确成员差异，且发布失败不产生部分成员快照或审计。
- 本地 Worker/D1 回归覆盖上述分支；不执行 preview/production 迁移或部署。
