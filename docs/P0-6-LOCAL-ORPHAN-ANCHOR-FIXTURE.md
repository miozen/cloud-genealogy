# P0-6 local-only 挑战账本独立测试锚点

状态：2026-10-31，仅隔离测试和设计评审；没有人工审批、业务接口或远程执行。测试使用私有临时 SQLite、一次性测试密钥以及单独的监督器和工作子进程，不连接 Cloudflare。

## 实验协议

测试监督器在自己的进程内存中持有测试账本摘要；它不直接打开 SQLite，摘要由受控测试调用方向它传递。测试初始基线覆盖夹具元数据、挑战状态、审计行和相关 SQLite schema，采用固定顺序和 SHA-256。测试工作进程经父进程转发 IPC 访问监督器，且在 `BEGIN IMMEDIATE` 持有写锁期间比较账本与锚点；不匹配、监督器无锚点或监督器处于待确认状态时拒绝。

对于有效签名，工作进程在 SQLite 事务中更新挑战和消费审计，计算新摘要；提交前监督器先记录 `pending(before, after)`，SQLite 提交后监督器才将锚点推进到新摘要。这个顺序并没有构造跨进程原子事务：若准备后、提交前中断，SQLite 回滚而监督器保持 pending；若提交后、确认前中断，SQLite 可能已经消费而监督器仍 pending。两种情况均阻塞后续受控消费，当前没有自动修复或人工解锁接口。若最终确认已完成但响应丢失，调用方可能不知道结果；重复挑战仍因 SQLite 已消费而拒绝。

测试在监督器存活时重启工作进程、回退 SQLite 快照、修改 schema、竞争消费，以及在提交前后分别强杀工作进程。还测试监督器丢失、监督器和工作进程在准备后同时丢失时的拒绝，和无效签名不消耗挑战。仅验证这些受控交错，不在 SQLite `COMMIT` 指令内或掉电时注入故障。

## 明确反例与信任边界

- **旧路径仍可绕过。** 这是新增测试函数 `guardedFixtureConsume`，现有 `ChallengeFixture.consume` 和 `issue` 没有强制经过锚点。测试恢复旧库后，受控路径检测到不匹配，但旧的无锚点 `consume` 仍可接受旧签名。因此不能宣称整个挑战账本具备防回滚能力，也不能接入真实执行。
- **锚点重置可回滚。** 监督器重启后内存清空并默认未初始化；测试保守调用路径拒绝消费。但测试 bootstrap 接口接受调用方提供的新基线：若从已回滚数据库重新初始化，旧签名会再次通过。对初始化权限、锚点遗失、监督器进程内存回滚和被盗用的防护尚未实现。
- **锚点并非独立信任根。** 监督器、IPC 调用方、SQLite 和工作进程都由同一测试用户控制；没有进程认证、可信存储、签名的初始化授权、跨机器隔离或防篡改硬件。恶意调用方可以伪造摘要或控制监督器，不能把该设计视为安全边界。
- **进度与可用性受限。** 当前只守护基线后的消费；直接签发新挑战或修改记录将导致摘要漂移，后续受控消费拒绝，未实现受控签发、锚点持久化或安全对账。监督器 pending 后需要外部设计恢复，不能盲目按数据库当前状态重新初始化。
- **不证明观察真实或新鲜。** 账本摘要和签名不能证明本地备份文件、冻结窗口、上传排空或审计来源可信；没有可信时间、密钥治理或真实双人审批。任何 future 操作均须另行设计与授权。

`npm run test:local-orphan-anchor` 验证上述受控路径、进程竞争/强杀、监督器缺失、回退与重新初始化反例。原有 challenge、signature 和 mock 测试仍应运行。
