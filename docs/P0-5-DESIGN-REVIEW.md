# P0-5 编修、审核与发布：设计审查

状态：受控变更首阶段已实现；本文保留为首切片设计基线。最后更新：2026-10-25。

## 已确认边界

- 编辑员只能创建、预览和提交变更提案；审核与发布必须由另一位具备 `lineage.review` 的管理员完成。已发布统一世系只读取不可变 revision snapshot，发布或回退不得覆盖历史 snapshot。
- 高风险变更（承谱、过继、拆支、挂接、合并、删除）必须先校验、预览、审核、审计并可回退；不得更改原始谱书记录或自动合并同名人物。
- 来源层、统一人物层、统一世系层和渲染层继续隔离。P0-5 的任何草稿不得出现在 P0-3/P0-4 的已发布读取 API 中。
- 现有 `lineage_published_pointer.version` 是发布时的乐观并发基线；陈旧版本必须返回冲突，不能静默覆盖。

## 现状与缺口

本文初稿时只有管理员直接 preview、publish、rollback。当前已具备持久化 `change_request` / `change_item`、编辑员范围校验、管理员队列、审核人指派快照、成员/结构条目、退休依赖预览与可审计草稿废弃。对象级审批规则及本文件列出的高风险扩展操作仍未实现。

## 建议的最小增量

1. 以 `change_request` 保存草稿、提交者、基准发布 revision、理由、状态和版本；以 `change_item` 保存明确的增删改意图，而非直接修改 snapshot。
2. 状态仅允许 `draft → pending_review → approved/rejected`；管理员发布已批准提案时，重新基于当前 pointer 校验并生成新的 immutable revision。若 pointer 已变化，提案进入冲突处理，不自动重放。
3. 预览端点从草稿项目构建候选关系，返回结构化校验错误、受影响人物/分支、承谱边与亲属关系差异；预览不写入权威世系。
4. 发布的 D1 batch 必须同时写 revision、snapshot、pointer、提案终态和 audit_log。来源主张、已发布 revision 与审计日志不物理删除。
5. 第一切片仅覆盖承谱边与 canonical relation snapshot；人物合并、拆支、删除和媒体引用应在各自风险模型与恢复策略明确后另开切片。

## 已确认的编辑员范围策略

- `account_scope` 的 `global` 与 `person` 可用于编辑员提案。`global` 必须由管理员显式授予；`person` 范围必须覆盖每一条 `change_item` 的双方人物。
- `branch` 范围只匹配提案基准 revision 的精确房支和 `blood_primary` 成员；不递归包含子房，不把 `migration` 或 `administrative` 成员当作编辑授权，也不能由承谱边或亲属关系自动推导。
- 管理员替换范围时以账号 `version` 乐观并发控制并写入 `audit_log`。编辑员在创建、预览和提交时均重新检查当前范围；撤销范围后，旧草稿不能继续提交。
- 提案创建者不得批准、驳回或发布自己的提案，防止单人绕过审核闭环。
- 关系提案发布时原样复制基准 revision 的 `branch_membership_snapshot`；提案不隐式增删房支成员。跨房支关系的双方都必须由显式人物范围或已授权房支覆盖。

## 验收与风险

- 编辑员无法绕过审核读取或写入正式世系；草稿与已发布视图严格分离。
- 管理员可看到基准版本、差异、校验结果和冲突原因；回退重新发布历史快照，不删除审计。
- 需增加本地 Worker/D1 集成回归，覆盖草稿、审核、陈旧指针冲突、非法环路、审计原子性和回退。
- 本阶段不替代 P0-6 的备份恢复演练；数据库迁移须有可测试的恢复方案。

## 需在实现前确认的事项

1. 人物合并、拆支、删除是否纳入 P0-5 首切片；建议不纳入，先完成承谱与亲属关系提案闭环。
2. 房支成员的创建、变更、来源依据和对象级审批人策略；这些能力必须独立于关系提案建立恢复与审核模型。
