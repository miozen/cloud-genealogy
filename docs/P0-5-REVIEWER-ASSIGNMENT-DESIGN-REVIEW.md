# P0-5 对象级审批人、代理与失效：设计审查

状态：已确认；首个按世系显式审核人指派切片已实现并完成 local Worker/D1 验证。最后更新：2026-10-24。

## 已验证现状

- 当前角色只有 `member`、`editor`、`admin`；只有 `admin` 具有 `lineage.review` 和 `system.manage`。`change_request` 只记录实际审核人和审核时间，不保存“应由谁审核”的指派信息。
- `account_scope` 的 `global`、`person`、`branch` 只用于编辑员创建提案的范围校验。房支范围仅覆盖提案基准 revision 中该房支的精确 `blood_primary` 成员，不递归子房；它不是审核授权，也不应被自动复用为审核授权。
- 结构和成员变更仍仅允许管理员创建、审核、发布。现行保护是创建者不得审核、驳回或发布自己的提案，另一位管理员可完成审核和发布。
- 提案可以同时包含关系、成员和房支结构条目，并可能涉及多个人、多个房支或新建房支。因此不能从单一 `branch_id` 推断唯一“负责人”。已退休房支和 revision 历史快照也不能被静默重写以改变旧提案的审核解释。

## 不可突破的约束

- 审批人资格必须由服务端在提交、审核和发布时校验；前端显示或隐藏不构成授权。
- 创建者永远不能审核、驳回或发布自己的提案；代理人同样不能绕过此规则。
- 授权、代理、撤销和过期必须留审计，且不得改写已发布 revision、来源记录或既有审计。
- 一项提案若跨越多个对象范围，必须明确全部命中规则；不能因存在一个宽泛房支范围而扩大对其余对象的审批权。
- 已提交提案的审核资格应有可解释的快照；授权随后变化时，系统应重新校验并在必要时要求重新指派，而不是静默改变历史责任。

## 方案比较

### 方案 A：按世系的明确审核人指派（推荐首切片）

管理员显式为一个 `lineage` 指派可审核账号，记录生效起止时间和授予人。提交时将符合资格的审核人候选快照写入提案；审核、发布时再次确认指派仍有效、审核人不是创建者且有 `lineage.review`。代理不单独推断：管理员直接为代理账号建立另一条同范围、带到期时间的指派。

优点：边界最清楚，跨房支/新房支提案天然适用；不把编辑范围误用为审核范围；能以最少新模型保留双人职责分离。缺点：尚非“按房支负责人”审批，需要管理员维护世系级候选人。

### 方案 B：按房支或人物的审核人映射

为 `branch`、`person` 或 `lineage` 建立映射；提交时根据每个条目和基准 snapshot 求影响对象集合，并要求审核人覆盖全部对象，或由多个审批人分别确认。

优点：职责粒度更细。风险：关系条目天然涉及至少两人，结构 create 没有既存房支，迁移/行政成员不等于血缘房支；还需定义跨房支、无主房、历史回退及多个审核人中的拒绝/过期语义。未经这些规则确认，不应实现。

### 方案 C：房支负责人自动成为审批人

不推荐。当前没有“负责人”事实来源，也没有从成员身份、账号关联、角色或谱书记录自动推断职责的可靠规则；自动推断可能错误授予高风险发布权限。

## 推荐的最小数据与流程（仅方案 A）

1. 新建 `lineage_reviewer_assignment`：稳定 ID、`lineage_id`、`reviewer_account_id`、`valid_from`、`valid_until`、`granted_by_account_id`、`revoked_at`、`revoked_by_account_id`、理由与创建时间。`valid_until` 必填，`valid_from < valid_until`；同一账号可续期但活动区间不得重叠。
2. 提交时，服务端从**当时有效**指派中选出候选；排除创建者。若候选为空，返回明确错误，不进入 `pending_review`。提案保存候选账号 ID 的不可变指派快照及其原始 assignment ID。
3. 审核/驳回时，审核人必须同时具备 `lineage.review`、属于提交快照候选、当前 assignment 未撤销且仍在有效期内，并且不是创建者。发布再次检查同一条件；过期或撤销则提案保持 `pending_review`，需要管理员重新指派并留审计，而不自动换人。
4. 代理是管理员显式创建的独立、短期 assignment，不建立无限递归的“代理链”。代理不可授予他人、不可修改指派、不可审核自身提案。原审核人撤销不自动撤销代理；管理员须显式撤销或等待到期。
5. 管理员保留紧急审核资格仅作为单独的、必须填写理由的受控覆盖；是否允许该覆盖需要业务确认。若允许，覆盖须记录原因、操作者和提案 ID，且仍禁止自审。

## 已确认的业务决定

1. 首切片采用方案 A（按世系显式指派），继续禁止从房支成员、账号关联或谱书内容自动推断审批人。
2. 指派有效期必填，最长 90 天；到期必须由管理员续期。
3. 默认不允许管理员绕过指派直接审核；紧急覆盖如有需要必须另行设计，不混入普通审核链路。
4. 代理只允许管理员创建的独立短期同世系指派，禁止层级转授权和自动继承。
5. 指派在提交后被撤销或到期，提案保留 `pending_review` 并要求重新指派。

## 已实现的首切片

- `0014_lineage_reviewer_assignments.sql` 新增带有效期、撤销信息、理由、版本与审计关联的世系审核人指派，以及提交时捕获候选审核人的 `change_request_reviewer_assignment` 快照。
- 管理员可列出、创建、撤销指派；只有当前活跃且具有管理员角色的账号可被指派，活动区间不得重叠。
- 新提案提交时必须存在有效、非创建者的指派审核人；审核与发布都会再次验证快照、当前有效期、撤销状态、账号活跃状态和管理员角色。迁移前没有审核人快照的既有提案保留原“另一管理员”规则，避免被静默搁置。
- local Worker/D1 集成回归实际覆盖显式指派完成的提交/审核/发布，以及撤销后新草稿返回 `reviewer_assignment_required`。未执行 preview/production 迁移或部署。

## 进入实现前的验收要求

- 本地 D1 migration 可前向应用并有不覆盖数据的恢复方案；不执行 preview/production 迁移。

- 现有“任意另一管理员审核”行为仅在迁移策略被明确确认前保留；不得在没有回退或切换方案时静默收紧已提交提案的审核资格。
