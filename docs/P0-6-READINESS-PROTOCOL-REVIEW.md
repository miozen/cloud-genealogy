# P0-6 写入范围、恢复证据与 readiness 协议审查

状态：设计建议和本地反例模型，尚未批准、尚未接入应用；真实备份执行和任何远程资源操作仍禁用。源码基线：`f188977`；审查日期：2026-10-29。源码中的 local 行为不代表 preview 已部署或已迁移。

## 1. 结论和当前真实行为

当前 `readiness` 是某个 D1 查询时刻的诊断快照，不是锁、授权、备份一致性证明或能跨导出过程保持有效的租约。它只在有活动冻结且所有未完成准入计数为 0 时报告 `apiWritesDrained`；无论上传计数如何，`uploadsDrained` 与 `remoteExecutionAvailable` 固定为 false。`blockers` 最多返回 100 条准入和 100 条上传并报告截断；它没有恢复接口，也不读取测试夹具恢复记录。冻结可通过独立管理接口解除；即使先后再冻结，查询结果也不能证明中间未解冻。

恢复测试的独立记录与审计只存在临时 SQLite；原准入 `completed_at` 没变，实际 API 仍将它计入在途。保留该行为，直至独立状态、证据和恢复执行器经过单独批准并验证。**本文件不是部署、读取或写入 Cloudflare 资源的授权。**

## 3. 官方平台行为依据

- [D1 batch 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/)说明批次顺序执行，语句失败回滚整批；这支持 D1 同批业务、状态、审计的设计，不提供 D1/R2 跨服务事务，也不保证客户端在中断时知道提交结果。
- [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)说明 HTTP 请求在客户端连接期间没有固定 wall-time 上限，断连后任务可能取消；因此准入记录年龄、固定等待、单个进程终止或 `finally` 并不足以证明全局排空。
- [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)明确 URL 在到期前可重复使用，签名生成无需与 R2 通信。当前实现签入 content-type 和 checksum、默认 5 分钟，但这不等于已开始请求完成或所有 R2 写者被隔离。
- [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/)说明负读取只证明读取时对象不存在，先前仍在途 PUT 之后仍可能提交；同键最后完成写入获胜。文档还说明 `If-None-Match: *` 在提交时原子判定。它可用于未来 create-once 设计的研究，不能自动约束历史已签发 URL 或证明 D1/R2 原子；R2 权限变更具有最终一致性。

## 4. 建议的状态与证据契约（未实现）

1. 正常准入状态保持 `open`、`normal_completed` 的事实；独立恢复案件记录 `requested → evidence_review → approved → recovered`，以及 `rejected`、`expired`、`needs_review` 等终态/人工复核状态。`recovered` 不改写正常 `completed_at`，不可重复覆盖，唯一绑定准入、冻结 ID 和递增代次。
2. 发起与审核分别由不同、当时有效且授权的身份完成；记录理由、权限判定、审批对象和不可变审计。夹具的两个账户 ID 不构成真实独立认证或审批。审批仅确认证据审查，不能创造技术排空事实。
3. 证据必须由可验证的采集者产生，绑定目标环境、数据库/桶身份、冻结 ID/代次、写者清单和版本、隔离范围、采集时间、有效期限及证据来源；验证者须验证来源、完整性、范围、时效和撤销状态。哈希只能绑定内容，不能证明内容真实。现有系统没有可信跨实例停止证明的采集器，也没有已批准的身份/密钥体系。
4. 在同一 D1 事务内重新核验冻结仍有效、代次未变化、准入仍未正常完成、审批与证据仍适用，并原子提交恢复终态及审计；重复相同请求可幂等读取，参数/证据变更、重复申请、撤销/过期、旧冻结和正常完成竞态必须拒绝或转人工复核。
5. 写者范围包含当前与旧 Worker、绑定/服务调用、所有 R2 凭据和可访问该数据的外部工具。写者未穷尽、策略更新或证据失效时全部回到未知/阻断。无法证明仍在运行的请求已停止，或无法证明所有副作用已隔离时，保持 `open` 阻断；固定等待、操作人声明和本地模拟均不够。

这些字段、状态和双人审查是推荐方案，不是已确认需求或生产实现。特别是直接推断“旧代次必然安全”不够：必须证明所有实际业务写和外部对象写均被适当 fencing，而且安全地处理已提交但响应丢失的结果。

## 5. 推荐的 blockers/readiness 语义（未实现）

- 单一、同源、可重复核验的快照应包含环境、冻结 ID/代次、采样时间、全量计数、分页/截断与已应用策略版本；明细与总数应有一致快照或明确版本，不能把前 100 条视为全量。缺失、错误、过期、截断或未知状态一律阻断。
- 按原因区分正常在途、疑似中断、恢复待审、恢复证据失效、历史上传 URL、未确认 PUT、未知外部写者及策略/迁移不匹配；不能用 `recovered` 的数量静默抵消实际开放记录。应用尚未实现此状态投影。
- 建议将 `D1 准入状态`、`外部写者覆盖`、`R2 上传排空`、`备份窗口仍被持有`、`恢复授权` 分开报告；每个值允许 `unknown`，未知与 false 均不得变成可执行。已有 `apiWritesDrained` 只能保留为该次计数事实，不能解释为全局已静默。
- 不用只读快照跨越 D1 导出、R2 清单和下载：未来需与冻结同一代次绑定的窗口协议，针对释放/重新冻结/配置变化/证据撤销进行原子或受控失效，并在导出前、期间及完成前校验；仅“前后各读一次”不能证明中间无释放及外部写入。具体 lease/审批机制需另行设计和授权，不能声称已有原子跨服务快照。
- 未实现可信 evidence adapter、R2 排空证明和窗口约束时，`uploadsDrained` 与 `remoteExecutionAvailable` 均继续为 false；候选方案和测试模型不能改写该事实。
